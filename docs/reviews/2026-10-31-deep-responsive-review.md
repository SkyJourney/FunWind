- 本轮目标：独立检查修复语义与测试盲区，并验证管理员/版主前台操作区、后台上传与素材界面的跨尺寸显示。
- 状态口径：站长本次明确确认 M9.6、M11.1 原则性收口，当前状态同步为 ✅；这不代表本轮新增了真人/真机测试，历史执行证据不改写。

- 本报告只把实际阅读、复现、命令输出与目视检查写作完成证据。源码风险候选与已证实缺陷分开。

## 2. 自适应布局契约

1. 内容区可以收缩（`min-width:0`）；长文件名/说明按语义断行或截断，截断必须保留完整内容的可访问方式。
2. 操作区与时间、说明、文件名分离。动作组使用 flex 换行，动作按钮内部保持单行、不压缩。
3. 输入/选择器有最大宽度和合理的弹性基准，空间不足时整组换行，不挤瘪相邻按钮。
4. 素材卡根据自身可用宽度排布；优先内在尺寸、auto-fit/minmax，需要结构变化时使用容器查询。
5. 表格/代码区允许局部滚动，不允许撑宽整页。禁止全局裁切来隐藏布局缺陷。
6. 不使用 UA 或 `isMobile` 分叉，不为手机复制一套动作 DOM；布局整改不能改变权限与服务端写入语义。

## 3. 复审发现与证据

### R-01：G-19 冲突草稿恢复与乐观锁（基线反例已证实，已修复）

- 基线页冲突后使用服务端最新 revision 与客户端旧草稿再次保存，会绕过原有乐观锁并静默覆盖其他管理员的更改。基线 theme-manager E2E 只做 `revision+1`、没有改真实并发内容，且期待直接再保存成功，不能证明安全恢复。
- 同一组实际页面接线测试对 `60c0ff3` 做隔离复验 4/4 失败：并发保存的名称/说明丢失；`surfaces` 新引用触发草稿清除；StrictMode 首次 effect 写入非用户定义；同一浏览器切换账号可恢复他人草稿。
- 首轮主题页面/表单/草稿专项 5 文件 67 项通过后，最终只读复核再发现两项数据丢失反例（修前 2/2 失败）：残留 `saved=1` 加上提交期间的旁路 revision 刷新会误判成功清稿；严格 schema 将可编辑中间态当坏档而丢掉完整草稿。最终增加每次提交 UUID 与服务端成功 `ack` 的精确匹配，以及草稿结构恢复与严格预览校验的分离；空 asset、超限数值、JSON 数值 null 可无损恢复，损坏结构拒绝恢复。专项最终 6 文件 79 项、加渲染/入口/架构守卫共 12 文件 150 项通过。`tsc --noEmit`、专属 ESLint/Prettier 通过，真实保存并发 E2E 也已在最终全量运行中通过。
- 完整草稿按账号+主题包键控，包含名称、说明、定义和原 `expectedRevision`；冲突保留旧版本并禁用提交。必须明确确认放弃当前草稿、载入服务端最新快照之后才可重新编辑，禁止自动升 revision 覆盖并发更改。浏览器存储禁用时保留当前页面内存工作并提示；离开当前页面后的恢复无法保证。
- **纠错：**上轮 effect 无依赖数组的计数器统计的是 effect 执行次数，不是挂载次数；不能据此断言 RSC 树整体重挂载、Flash 插入是原因或排除插槽问题。该根因解释已撤回。StrictMode 证据是首次 effect 可能写入非用户初始快照，不能夸大为“必然最终丢稿”。

### R-02：批次 0–4 独立复审的范围内修复

- **G-11 与 Server Action 导出守卫：**G-11 符号来源解析曾漏掉字面量 `require()` / `import = require()`；use-server-export 守卫行首正则曾漏掉指令前注释和单声明多绑定。新增合成反例后重写 AST 逐来源/逐绑定检查，修前 G-11 8 项、Action 5 项失败，最终 5 文件 106 项通过；`tsc --noEmit --incremental false` 通过。
- **邮件/账号时序（批次 0/1）：**换绑后旧邮箱仍被提示用已解绑邮箱找回；注销邮件资格分支令存在 challenge 与不存在 challenge 的响应分别等待/不等待 SMTP。告警改为真实安全路径，签发与发送移至 `after()` 后中性响应。
- **主题导入/媒体池（批次 2）：**导入补偿曾恢复旧 active 快照并覆盖并发管理员选择。导入素材改为非激活入池；补偿不得删除并发选为 active 的新素材，并告警。
- **版主元数据（批次 3）：**共享 `ForumSelect` 曾向板块范围版主下发全树（包含不可读板块名称/id）。现基于真实主体过滤：站长保留全树，其他主体仅取授权板块；空集合不回退全树。
- **PM 邮件附带故障（批次 2/3）：**通知已提交后邮件偏好/邮件发送故障曾使事件整体失败并重放，造成通知聚合 count 增长；窄修只隔离站内通知后的邮件副作用。真实临时库反例修前 count 2/4/6、修后 1/3/5，消息均保持 1 条。
- **仍未解决：持久 outbox 幂等。**另行模拟“通知消费者事务已提交、outbox dispatched 标记未提交”再 drain，消息 1 条但聚合 count 由 1 增至 2。`notify.ts` 聚合行及 outbox 状态之间没有持久消费回执；本轮不新增 schema/事件契约，必须作为后续数据层幂等设计项，不能宣称 exactly-once。
- **审核与权限写路径（批次 2/3）：**锁内重验审核状态以防迟到 approve 复活 hidden/deleted；回帖列表排除主题首帖；PM 发送方注销竞争在锁后校验；待审回帖批准通知保留回复对象；审核/内容分页同秒增加唯一键。随机临时 MySQL 集成覆盖，相关修复工作组 8 测试文件 140 项通过。
- **媒体（批次 4）：**动画 GIF 坏帧先前可能仅通过 metadata/块检查。现对动画做逐帧解码校验，不创建像素 raw buffer、不重编码；总解码像素受现有 40,000,000 上限约束，保留合法动画数据。坏帧/有效动画与上限相关用例纳入 process-image/GIF 定向测试。
