## 1. 目标

M11.2 的 effect 都是「视觉类」：只替换读取到的站点默认值，没有副作用，写坏了也只是回退常态。
M11.3 把同一套排期引擎扩到**行为类** effect——在时间窗内临时改变一个业务决策点的取值：

- **开放注册窗口**：活动期内把注册模式从邀请制临时放开，到期自动回到邀请制。
- **积分加成**：活动期内临时提高发帖 / 回帖 / 签到的奖励额。

表结构不动（`campaigns.effect` + `config` 已能容纳）；注册表接口需先扩展（Step 0），再加注册项和各自的消费点。

**范围扩大（2026-11-03 站长对 Q1 的回答）**：开放注册不只是排期窗口，站点设置里也要能**独立开关**开放注册与邀请注册，
并支持「开放注册需验证邮箱、不验证无法登录」。这块「注册策略基线」独立于排期，是本草案里改动面最大的部分（§2.1、§4 Step 1）。

### 2.1 站长 2026-11-03 对 Q1 的回答所涉及的现状（邮箱验证与登录）

站长要求：开放注册与邀请注册在站点设置里**各自独立开关**；开放注册可设邮件验证，**不验证无法登录**。已核实：

| 事实 | 位置 | 影响 |
|---|---|---|
| 注册模式现在是**单选**（`invite` \| `open`），没有「两者都开」或「两者都关」 | `lib/auth/settings.ts` 的 `RegisterMode`；`app/admin/settings/page.tsx:266-300` | 两个独立开关意味着从单选改为两个布尔，要定义四种组合（§6 Q7、Q8），并兼容旧 `register.mode` 数据 |
| 邮箱验证门**只拦写权限，不拦登录**：评估器对 `isWrite && emailVerificationRequired && !emailVerified` 返回「请先验证邮箱」；登录流程 `attemptLogin` 完全不看验证状态，`LoginOutcome` 只有 `throttled` / `invalid` 两种失败 | `lib/authz/evaluator.ts:110-118`；`lib/auth/login.ts:37-45` | 「不验证无法登录」是**比现状严格得多的新行为**，需要新增登录失败分支、对应提示与测试，不是改个开关 |
| 重发验证邮件的入口在 `/settings/email`，**需要已登录** | `app/settings/email/page.tsx:75`；`resendEmailVerificationAction` | 若登录被拦，用户无从重发验证邮件，会**永久锁死**；必须提供免登录的重发路径（§6 Q9） |
| 改绑邮箱会把 `emailVerifiedAt` 置空并把 `emailVerificationRequired` 置真 | `lib/auth/email-change.ts:51-59` | 叠加登录门后，已登录用户改邮箱（包括填错）下次登录就被拦，且新邮箱收不到信就无法自救 |

| 开发库现状：活动用户 10,698，有邮箱 10,679，**已验证 0，要求验证 0** | 只读统计 `qysub_next` | 若登录门误写成「未验证即拦」，会**一次性锁死全部导入用户**。必须按上一行的口径判定，并为此写回归用例 |

## 3. 与视觉类 effect 的本质差异（设计必须正视）

M11.2 的「坏配置只忽略该行、回退常态」对视觉类是对的，对行为类**不一定对**：

1. **有副作用，且不可撤销。** 开放注册窗口内创建的账号、加成期发出的积分都是写入库的事实，窗口结束不会回滚。
   因此这类方案的「保存时校验」必须比视觉类严格，「配置看起来合法但意图错误」的代价是真实的账号和积分。
2. **读取点分散，一致性靠单一入口。** 视觉类只有 `getSiteChrome` 一处合成；行为类要覆盖决策点本身，
   必须保证**每个消费点读到同一个值**，否则出现「页面显示开放、提交被拒」这类不一致。
3. **失败方向不同。** 视觉类读失败 → 回退常态（安全）。注册模式读失败回退「邀请制」也是安全的（保守）；
   但积分加成读失败回退「无加成」会让活动期内用户少拿积分，需要决定是否记录告警（§6 Q4）。
4. **审计要求更高。** 视觉类只记方案增删改；行为类应能回答「某笔积分 / 某个账号是在哪个方案生效期间产生的」。

## 4. 范围与 Step 分解（Q7–Q10 拍板后细化）

> **范围已超出最初设想。** 站长对 Q1 的回答带来了一整块「注册策略」改造（两个独立开关、关闭态、登录门、免登录重发），
> 它是**独立于排期引擎的站点基础能力**，即使没有任何排期也要成立。建议拆成两个里程碑（Q10）：
> 先做「注册策略基线」，再在其上做行为类 effect。下面的 Step 按建议的拆法排序，Step 1 属于基线，Step 2–4 属于 effect。

**Step 0 · 扩展注册表以容纳非「单字符串目标」的 effect**
- 把 `targetKey` 单目标假设换成通用形态：effect 自己声明表单字段（0 个、1 个枚举选择、或数值输入）及其与 `config` 的互转，
  表单据此渲染。M11.2 的三个视觉 effect 迁移到新形态后行为必须完全不变（`chrome-compose.int` 与 `campaigns.spec` 原样通过）。
- 这是本里程碑最大的结构性改动，且动到 M11.2 刚收口的代码，应单独成一个提交、单独过全量门禁。

**Step 1 · 注册策略基线（站点设置，与排期无关）**
- 站点设置新增策略键（建议 `register.policy`）：`{ open: boolean, invite: boolean, openRequiresVerification: boolean }`。
  两个开关独立；旧 `register.mode`（`invite` \| `open`）按 `invite → {open:false, invite:true}`、`open → {open:true, invite:false}` 读兼容，
  不做破坏性迁移，写入新键后旧键不再参与判定。
- `getRegisterMode()` 的消费点只有注册页与注册 Action（§2）；改造后这两处按四种组合分支（§6 Q7、Q8）。
- **登录门**：`LoginOutcome` 新增失败分支（如 `unverified`），判定口径固定为「该账号 `emailVerificationRequired` 为真且 `emailVerifiedAt` 为空」，
  **不是**「未验证即拦」（§2.1 末行：否则 10,698 个导入用户被一次性锁死）。登录页给出明确提示而不是笼统的「用户名或密码错误」。
- **免登录重发验证邮件**：登录被拦的页面提供重发入口，沿用邮件令牌的既有限流与「防枚举」中性响应（同忘记密码的口径），
  不暴露账号是否存在。没有这一项，登录门不得上线。
- 测试：四种开关组合 × 邀请码有无；登录门只拦「要求验证且未验证」；导入用户（要求=0）登录不受影响；改绑邮箱后的自救路径（§6 Q9）。

**Step 2 · 注册模式 effect（`register.open`）**
- 注册 effect：`config: { }`（无参数——生效即「开放注册开关为开」）；读侧在 Step 1 的策略之上叠加，**只能放开不能收紧**
  （排期结束必须回到站点设置的原值，不能因排期把站点设置里的「关」永久改成「开」）。
- 开放窗口内沿用 Step 1 的验证与登录门配置，以及已有的限流和全局兜底桶（IP 未知时 60 次/小时），不绕开防刷。

**Step 3 · 积分加成 effect（`points.boost`）**
- 整数倍率（×2、×3，Q2）；作用渠道限 `earn.post` / `earn.reply` / `earn.checkin`；日上限同比放大（Q3）；签到放大最终结果（Q6）。
- 改点只在 `awardEarn` 与签到取奖励处：加成后的金额进入既有的事务、日上限判定与幂等键，**不新增渠道、不改台账结构**。
- 台账 `note` 注明「（活动加成：方案名）」，使 §3 第 4 点可追溯；读不到方案时回退「无加成」并记一条带方案上下文的 warn（Q4）。
- 行为类 effect 保存时拒绝同 effect 窗口重叠（Q5）。

**Step 4 · 后台与收口**
- `/admin/campaigns` 表单加入新 effect 的目标 / 参数输入；行为类方案在列表里与视觉类**视觉上区分**并提示「会产生不可回滚的副作用」。
- E2E（窗口内开放注册、窗口外回到邀请制、加成期发帖拿到加成额、到期恢复）；THEME-SYSTEM / POINTS / CHANGELOG 回写。

## 5. 边界（明确不做什么）

- 不做邀请码发码额度 / 会员自助发码——代码里没有这个概念可覆盖（§2），要做是新功能，应单独立项。
- 不做「到点自动发奖」（活动结束时批量发积分 / 徽章）：那是 pending 行 + 批处理 + 幂等键的另一类机制，
  不属于读取覆盖，见 [M11.2](M11.2-theme-switching.md) §6。
- 不做按用户群 / 版块差异化的加成；不改积分台账结构、不新增积分渠道（POINTS.md §3「新渠道需模块声明」不变）。
- 不改权限判定引擎。`Subject.registerMode` 的取值来源变了，但评估器逻辑不动。

### 6.2 待确认（由 Q1 的回答引出，每条带建议默认值）

- **Q7 两个开关都开时怎么办**：访客同时可以开放注册和用邀请码注册。邀请码栏是否保留？填了邀请码和没填，验证要求是否不同？
  *建议：邀请码栏保留且选填。填了有效邀请码 → 按「邀请注册」规则（受 `email.verification` 现有的 `open_only` / `always` 策略约束）；
  留空 → 按「开放注册」规则（受 `openRequiresVerification` 约束）。填了无效邀请码一律报错，不降级成开放注册，避免悄悄绕过。*
- **Q8 两个开关都关时怎么办**：现有系统没有「注册关闭」这个状态。*建议：注册页显示「当前不开放注册」，注册 Action 一律拒绝并不消耗限流名额；
  已有账号的登录、找回密码、邮箱验证链接不受影响。*
- **Q9 「不验证无法登录」的范围与锁死风险**（§2.1 列出的三处风险）：
  (a) 登录被拦的用户如何重发验证邮件？*建议：登录页在该失败态给出免登录的「重发验证邮件」入口，沿用忘记密码的中性响应与限流，不暴露账号是否存在。*
  (b) 已登录用户改绑邮箱后验证状态被重置，叠加登录门会让他下次登录被拦；填错邮箱则永久锁死。*建议：登录门**只对注册时就要求验证的账号生效**；
  改绑邮箱造成的「重新验证」仍只拦写权限、不拦登录，保持现状。这样登录门不会因改绑把人锁死。*
  (c) 已登录的未验证账号的现有会话怎么办？*建议：不踢出现有会话，只拦新登录；登录门上线后新注册的账号才受影响，历史账号零影响。*
- **Q10 是否拆成两个里程碑**：上面的「注册策略基线」（两个开关、关闭态、登录门、免登录重发）本身就是一个完整的功能，
  与排期引擎无关。*建议：拆开——M11.3 只做注册策略基线，M11.4 再做行为类 effect（含 Step 0 的注册表扩展）。
  好处是基线可以先独立上线验证，不被排期引擎拖住；effect 依赖基线的开关语义，顺序也自然。*

## 7. 测试规则

- 单测：新 effect 的 schema（无参数 / 倍率范围），选优与重叠拒绝（若 Q5 采用禁止重叠）。
- 集成（真实临时 MySQL）：窗口内 / 外 / 边界时刻；`getRegisterMode` 与 `Subject.registerMode` 一致；
  加成金额进入日上限判定与幂等键不变；并发发帖下加成与上限仍精确（沿用 `earn` 现有并发用例的口径）。
- E2E：开放窗口内无邀请码可注册、窗口外被拒；加成期发帖入账额正确且台账可追溯；**每条新业务线至少一条错误路径**（G-16）。
