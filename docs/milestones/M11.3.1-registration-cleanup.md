## 2. 管理员代改邮箱并重新发起验证

**问题**：用户注册时填错邮箱，登录门把他挡在外面，免登录重发又发回同一个错地址，用户名同时被占用。此前站长没有任何后台手段，只能改库。

**行为**（用户详情页 `/admin/users/[uid]` 新增「邮箱与验证」卡片，权限 `admin.users`，越权 404）：

- 事务内锁行、查重、改邮箱、置未验证、清旧令牌、签发新验证令牌、写审计，复用 `changeEmailAddress`，仅新增可选的审计参数；**自助改邮箱的行为不变**。
- **不动登录门**：注册时填错邮箱的账号，门要等用户点新地址里的链接才解除（首次验证成功即清除），这就是自救闭环。已验证账号被改邮箱，只回到「写权限受限」，不拦登录（沿用 M11.3 Q9b）。
- 目标账号检查与限制、角色授予同口径：已注销、注销冷静期的账号一律拒绝。
- **旧地址告警只发给被用户验证过的旧地址。** 没验证过的地址从未被证明属于该用户（填错的邮箱可能是陌生人的），向它发「账号邮箱已更换」会让陌生人知道该地址在本站注册过。已验证账号沿用自助路径的告警加新地址确认。
- 同邮箱再提交：未验证账号当作重发验证邮件；已验证账号提示「邮箱未变化」。
- 目标地址限流沿用 5 次/小时，防止借管理员入口给第三方邮箱刷信。
- 审计：操作者是管理员，动作 `admin.user.email.change`，邮箱只记哈希不记明文。
- 详情页状态文案：登录门账号原来写「邮箱待验证（写入受限）」不准确，改为「注册后未验证，无法登录」。

## 3. 超期未验证账号清理

**判定**（SQL 谓词，条件刻意收紧，每条都有变异测试）：`state=active`，且登录门仍关着，且 `email_verified_at` 为空，且 `last_login_at` 为空，且没有任何会话行，且 `created_at` 早于 N 天前。所以导入的历史账号、邀请注册账号、已登录过的账号永远不会被选中。

**动作**：复用账号注销用的 `purgeUserDataInTx`（用户名改占位 `已注销用户#id`、清邮箱、置 `state=deleted`），释放用户名与邮箱。不另写删除逻辑：本库没有外键，引用完整性全靠应用层，另写一份会在新增引用用户的表时漂移。每个账号单事务，**加锁后重新核对全部条件**——选出候选到清理之间用户可能刚好点了验证链接，此时放过。审计只记账号 id、注册时间与天数，不记邮箱。

**顺带修复**：`purgeUserDataInTx` 原来重置了 `emailVerificationRequired` 却漏了 `loginVerificationRequired`，清理后的行会留着无意义的登录门标记。已补，并先改测试看它变红再改实现。

**命令行**：`pnpm --filter @funwind/web unverified-accounts:purge [--apply] [--days=7] [--limit=200]`。默认只报告；`--days` 必须是不小于 1 的整数；有账号清理失败时退出码为 1。

## 4. 视觉债清账

M11.3 收口时登记了三项既有视觉问题，查清后范围比当时报告的更大：

**浅色下四个语义色在各自 `/10` 淡底上都不到 4.5:1**（不只是 `--warning`）：

| 令牌 | 默认浅色（卡片底 / 页面底） | 情怀包 qy2010 |
|---|---|---|
| warning | 2.86 / 2.75 | 3.26 / 3.00 |
| success | 2.96 / 2.82 | 2.90 / 2.67 |
| destructive | 4.13 / 3.97 | 5.11 / 4.70（已达标） |
| primary | 4.67 / 4.49 | 4.08 / 3.75 |

暗色全部达标（最低 5.69）。使用面：`text-warning` 56 处、`text-destructive` 78 处。

**处理**（改令牌层，不逐处改——项目有先例：S3 把 amber-500 调到 600）：

| 令牌 | 改动 | 淡底对比度（卡片 / 页面） |
|---|---|---|
| warning | amber-600 → amber-800 `#92400e` | 6.08 / 5.80 |
| success | green-600 → green-800 `#166534` | 6.14 / 5.86 |
| destructive | red-600 → red-700 `#b91c1c` | 5.45 / 5.24；白字按钮 4.83 → 6.47 |
| qy2010 warning | `#b8770a` → `#8a5200` | 5.43 / 5.00 |

- `primary` 是品牌色，不动令牌；只对 AuthShell 蓝色提示条局部加深（primary 80% + 黑 20%）：默认 6.22，qy2010 5.34。
- **代价**：警示、成功、错误文字整体变深，淡底也略灰（警示条淡底 `#fbf1e6` → `#f4ece7`）。前后对比图见 `/tmp/vis-diag/token-compare.png`，**颜色是否定稿待站长看过**。
- **「显示密码」按钮 32px 不算违规**：WCAG 2.2 AA 要求 ≥24px，之前说「低于 36px 建议」并没有项目依据。视觉保持 32px（输入框只有 36px 高，放大会显得挤），用伪元素把点击热区外扩到 40px。
- **守卫**：`src/test/token-contrast.test.ts` 直接解析令牌 CSS，断言三套主题下这些语义色 ≥4.5:1。
- **已知缺口**：情怀包 primary 文字压在淡底上不足 4.5:1，未处理（改的是情怀包品牌色，待站长决定）。
- `test:visual` 8/8，基线一张都没变。

**顺带发现并修复的既有布局问题**：用户详情页下半部分的卡片网格在 320px 被隐式列撑出 44px。网格没有写 `grid-cols-1`，隐式列取了内容的最小宽度。两处各加一个类名。

## 5. 站长确认后的处置

1. **定时触发方式** → 进程内调度，[M11.5](M11.5-scheduler.md) 设计稿待确认。在它落地前，`unverified-accounts:purge` 保持「手动或 cron 调用脚本」的形态，默认只报告。
2. **`account-deletion:drain` 不会自行退出** → 已修（一行显式退出）。先写进程级测试看它变红（三项均因 60 秒超时失败），再改脚本变绿。实测复现的现象：输出结果后进程仍挂着，getWebDb 的连接池占着事件循环；用 cron 每调用一次就会留下一个不退出的 node 进程。`digest:run` 与 `outbox-drain` 本就有显式退出，只有它缺。
3. **颜色** → 站长确认定稿。
4. **qy2010** → 另立 [M11.6](M11.6-theme-semantic-tokens.md)。**核实结果：站长的判断是对的**——M11.1 §1.2 原定「qy2010 全部值数据化（语义色 15 项、阴影、radius、表面组、band 参数、宋体栈）」，实际引擎的 `ThemePackDefinition` 只有 `surfaces` 与 `pwa`，qy2010.css 里 41 条声明中的语义色 22 个、圆角阴影 4 个、板块卡参数 6 个、字体 1 个一直留在 CSS。所以「去掉 CSS」不是顺手的事，而是给引擎加一整层语义令牌。**情怀包 primary 文字压淡底不足 4.5:1 的缺口，由 M11.6 在迁移后单独微调品牌色解决**，`token-contrast.test.ts` 里的「已知缺口」注释保留到那时。
