## 1. 目标

M11.2 的 effect 都是「视觉类」：只替换读取到的站点默认值，没有副作用，写坏了也只是回退常态。
M11.4 把同一套排期引擎扩到**行为类** effect——在时间窗内临时改变一个业务决策点的取值：

- **开放注册窗口**：活动期内把站点设置里的「开放注册」临时打开，到期自动回到站点设置的原值。
- **积分加成**：活动期内临时提高发帖 / 回帖 / 签到的奖励额。

表结构不动（`campaigns.effect` + `config` 已能容纳）；注册表接口需先扩展（Step 0），再加注册项和各自的消费点。

## 3. 与视觉类 effect 的本质差异（设计必须正视）

M11.2 的「坏配置只忽略该行、回退常态」对视觉类是对的，对行为类**不一定对**：

1. **有副作用，且不可撤销。** 开放注册窗口内创建的账号、加成期发出的积分都是写入库的事实，窗口结束不会回滚。
   因此这类方案的「保存时校验」必须比视觉类严格，「配置看起来合法但意图错误」的代价是真实的账号和积分。
2. **读取点分散，一致性靠单一入口。** 视觉类只有 `getSiteChrome` 一处合成；行为类要覆盖决策点本身，
   必须保证**每个消费点读到同一个值**，否则出现「页面显示开放、提交被拒」这类不一致。
3. **失败方向不同。** 视觉类读失败 → 回退常态（安全）。注册模式读失败回退「邀请制」也是安全的（保守）；
   但积分加成读失败回退「无加成」会让活动期内用户少拿积分，需要决定是否记录告警（§6 Q4）。
4. **审计要求更高。** 视觉类只记方案增删改；行为类应能回答「某笔积分 / 某个账号是在哪个方案生效期间产生的」。

## 4. 范围与 Step 分解

> 站长 2026-11-03 确认拆分（Q10）：「注册策略基线」（两个独立开关、关闭态、登录门、免登录重发）已独立为
> [M11.3](M11.3-register-policy.md)。本里程碑只做行为类 effect，Step 编号保持原样以便对照，原 Step 1 已迁出。

**Step 0 · 扩展注册表以容纳非「单字符串目标」的 effect**
- 把 `targetKey` 单目标假设换成通用形态：effect 自己声明表单字段（0 个、1 个枚举选择、或数值输入）及其与 `config` 的互转，
  表单据此渲染。M11.2 的三个视觉 effect 迁移到新形态后行为必须完全不变（`chrome-compose.int` 与 `campaigns.spec` 原样通过）。
- 这是本里程碑最大的结构性改动，且动到 M11.2 刚收口的代码，应单独成一个提交、单独过全量门禁。

**Step 1 · （已迁出）** 注册策略基线见 [M11.3](M11.3-register-policy.md)，是本里程碑 Step 2 的前置依赖。

**Step 2 · 注册模式 effect（`register.open`）**
- 注册 effect：`config: { }`（无参数——生效即「开放注册开关为开」）；读侧在 M11.3 的策略之上叠加，**只能放开不能收紧**
  （排期结束必须回到站点设置的原值，不能因排期把站点设置里的「关」永久改成「开」）。
- 开放窗口内沿用 M11.3 的验证与登录门配置，以及已有的限流和全局兜底桶（IP 未知时 60 次/小时），不绕开防刷。
- 与 M11.3 的开关组合交互：站点设置若是「邀请开、开放关」，窗口内变成「双开」，此时邀请码选填的规则（M11.3 §3）直接适用。

**Step 3 · 积分加成 effect（`points.boost`）**
- 整数倍率（×2、×3，Q2）；作用渠道限 `earn.post` / `earn.reply` / `earn.checkin`；日上限同比放大（Q3）；签到放大最终结果（Q6）。
- 改点只在 `awardEarn` 与签到取奖励处：加成后的金额进入既有的事务、日上限判定与幂等键，**不新增渠道、不改台账结构**。
- 台账 `note` 注明「（活动加成：方案名）」，使 §3 第 4 点可追溯；读不到方案时回退「无加成」并记一条带方案上下文的 warn（Q4）。
- 行为类 effect 保存时拒绝同 effect 窗口重叠（Q5）。

**Step 4 · 后台与收口**
- `/admin/campaigns` 表单加入新 effect 的目标 / 参数输入；行为类方案在列表里与视觉类**视觉上区分**并提示「会产生不可回滚的副作用」。
- E2E（窗口内开放注册、窗口外回到邀请制、加成期发帖拿到加成额、到期恢复）；THEME-SYSTEM / POINTS / CHANGELOG 回写。

## 5. 边界（明确不做什么）

- 不做邀请码发码额度 / 会员自助发码——代码里没有这个概念可覆盖（§2），要做是新功能，应单独立项。
- 不做「到点自动发奖」（活动结束时批量发积分 / 徽章）：那是 pending 行 + 批处理 + 幂等键的另一类机制，
  不属于读取覆盖，见 [M11.2](M11.2-theme-switching.md) §6。
- 不做按用户群 / 版块差异化的加成；不改积分台账结构、不新增积分渠道（POINTS.md §3「新渠道需模块声明」不变）。
- 不改权限判定引擎；不做注册策略基线（两个开关、关闭态、登录门），那是 [M11.3](M11.3-register-policy.md)。
