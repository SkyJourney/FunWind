- 阶段：四·运营与演进 ｜ 依赖：M20 管理 REST 与令牌；M20.1 在线文档随本期同步，无运行时依赖。

## 1. 基线与边界

[M20](M20-admin-api-tokens.md) 上线了九个 GET。现有令牌没有独立授权，只复用持有人实时权限；如果只加写路由，旧令牌可能随之获得写权限。现有 `api.*` 审计在 handler 前记录调用，不证明变更成功；写 API 需要独立的变更审计、并发和重试约定。在线页实际位于 `/docs/rest-api`，渲染源为 `lib/manage/api-docs-md*.ts`，不是 M20.1 开工稿的拟议数据源。

**本期交付**：按域选择的令牌矩阵、旧令牌兼容迁移、内容单条审核及主题锁定/解锁、仓库契约与在线页同步。既有 Cookie / Server Action、九个管理 GET 的路径与原有字段语义保留。

**本期不做**：REST 自管理令牌、OAuth、逐版块令牌范围、批量写、内容删除/恢复、全站封禁、角色授撤、代改邮箱、积分及运维写。用户禁言/解除、公告、视觉排期留后续评估；不开放通用任意字段写入。M21 不在本期实现，即便 REST 已可写，MCP 写工具仍须逐项批准，并单独决定人工确认方式。

## 2. 权限矩阵

表内路径均相对于 `/api/manage`。基础资格统一保留 `site.admin` + `admin.roles`。

| 数据域 | 令牌权限 | 持有人与资源条件 | 旧令牌保留的端点 | 本期新增 |
|---|---|---|---|---|
| 令牌身份 | `identity:read` | 基础资格 | `GET /whoami` | — |
| 内容治理 | `contents:read` / `contents:write` | 读保留 `resolveContentScope`；写走既有内容治理判定与目标范围 | `GET /contents`、`GET /contents/{id}` | 单条审核、主题锁定/解锁 |
| 用户管理 | `users:read` | `admin.users`；敏感字段另需 `user.viewIp` | `GET /users`、`GET /users/{uid}` | — |
| 站点统计 | `stats:read` | `admin.logs` | `GET /stats` | — |
| 审计日志 | `audit-logs:read` | `admin.logs` | `GET /audit-logs` | — |
| 邮件日志 | `emails:read` | `admin.logs` | `GET /emails` | — |
| 推送日志 | `push-logs:read` | `admin.logs` | `GET /push-logs` | — |

1. **禁止**不授予该域任何入口；**只读**授予该域签发时已开放的读端点；**读写**授予该域签发时已开放的读、写端点。本期只有内容域可选读写；其余域明确标注尚无写端点。统计、审计、邮件与推送独立勾选，不因复用 `admin.logs` 而捆绑。`whoami` 也需 `identity:read`。
2. **矩阵用于选择，令牌保存稳定端点权限 ID 快照。** 同一域同一档将来新增端点，也不给已签发令牌自动补权。新增能力使用新 ID；不允许把更强的行为塞进旧 ID。页面展示签发时快照和精确端点清单；当现目录扩容时提示原令牌不含新增项。权限不可原地编辑，换发后吊销旧令牌。
3. **有效权限取交集**：令牌授权 ∩ 持有人实时资格与业务权限 ∩ 服务层资源范围及字段权限。签发时也检查持有人当下的全局权限；不授予无法通过该层检查的端点。请求中的资源判定由原业务服务完成，不以域权限代替。保留 M20 的过期、手动吊销与撤权联动。
4. 在 `apps/web/src/lib/manage/` 建立纯数据权限目录，统一定义域、级别、稳定 ID、HTTP 方法、路径、主体附加权限。路由、后台矩阵、在线文档共用目录；实际方法和路径必须与 ID 一致。派生的 `HEAD`、框架 `OPTIONS` 不独立授予数据权限、不得成为业务旁路；需验证方法不匹配不会命中处理器或泄露资源状态。未知方法绑定、未知授权模型、无效快照或前缀错配一律拒绝。

## 3. 兼容迁移、后台与退版

- **加法迁移**：`packages/db/src/schema.ts` 增加权限模型和授权快照，提交版本化迁移。旧行归为 `legacy_m20_read`，仅指向冻结的九个 GET（`whoami`、`contents`、`contents.detail`、`users`、`users.detail`、`stats`、`audit-logs`、`emails`、`push-logs`），不从实时目录重算。原前缀 `fw_at_`、哈希、到期、吊销及使用数据不改。加法列的历史模型默认值兼容旧版签发；该模型不得携带快照，新模型必须显式写入非空合法快照，不能把缺失模型、空快照解释为兼容旧令牌。验证覆盖现有库与零数据安装；不 seed、不导入令牌，`db:verify` 加模型/默认值与数据组合检查。
- **凭证隔离**：所有新版签发走 `fw_at2_`，包括仅有一项读权或选满权限的令牌；沿用安全随机生成与只存哈希。新版严格接受各自前缀，并与库内模型双向核对。旧版解析器不接受 `fw_at2_`；同库退版时新令牌 401，绝不会被当成旧九读令牌。退版窗口若使用旧后台签发，按 M20 原行为签出固定九读的兼容令牌，新版恢复后它仍只有九读。旧版可能仍将未失效的新令牌计入配额并允许吊销；恢复新版后，仅未吊销且未过期的新令牌恢复原权限。
- **后台**：`app/admin/api-tokens/` 新签发默认全禁，至少一个可用域；区分「业务权限不足」和「本域尚无写端点」，列表和详情展示矩阵与实际快照。Action 只接收域和档位，服务端归一化、重验白名单并展开 ID，拒绝客户端直传快照。保留名称、有效期、上限、一次性明文及吊销。资格、配额、签发与审计纳入受锁流程，覆盖并发争最后一个名额及签发与降权交错。
- **诊断**：`GET /whoami` 默认响应不变；可选 `include=token_permissions` 返回令牌精确授权，以及经当前全局资格与端点权限裁剪的能力，不承诺能作用于任何具体资源。继续不记调用审计、不更新 `last_used`。

## 4. 首批写端点与协议

| 方法与路径 | 令牌权限及稳定 ID | 请求与响应 |
|---|---|---|
| `POST /api/manage/posts/{postId}/review` | `contents:write` / `posts.review` | `{decision, expectedEditedAt, reason?}`。`decision` 为 `approve` 或 `reject`；`expectedEditedAt` 必传，可为 `null`。驳回理由去空白后 1–255 字，通过不接收理由。成功返回 `{postId, threadId, state}`，状态为 `visible` 或 `rejected`。 |
| `PUT /api/manage/threads/{threadId}/lock` | `contents:write` / `threads.lock` | `{locked: boolean}`，设置目标值而非翻转；成功返回 `{threadId, locked, changed}`。不开放置顶或精华。 |

### 4.1 业务复用与并发

- 审核复用 `lib/moderation/review.ts`、`lib/posting/transition.ts` 与现有 `forum.moderate` 判定。管理内容详情增补帖子 `editedAt`，主题从 `firstPost` 取得，回复从自身取得；区分 `postId`（PID）与 `threadId`（TID）。沿用 `posts.editedAt` 编辑并发口径：北京时间秒级值、同秒连续编辑严格递增。事务锁内核对目标归属、待审状态和审核版本；过期版本或不合法状态为 409。保持原审核历史、计数、通知、首次积分与事务 outbox 链路。
- 主题锁复用并收紧 `lib/moderation/contents.ts` 的 `setThreadFlags`；按现有管理员/版主规则判定。事务内锁目标、复核类型与范围，读旧值后更新并记录前后状态。同值返回 `changed: false`，不写变更审计；相反指令按锁内提交顺序串行，后提交的目标值生效。
- 路由保持「入口薄、Service 厚」。审核业务事务核心可由原后台 Action 与 REST 共用；不在 route 写 SQL，不嵌套事务，不从已持事务另借连接。复用现有内容锁序、死锁重试及 outbox 提交后派发约定。资格在请求入口复核，不承诺已通过检查的在途写可被后续撤销中止；资源归属与状态在锁内复核。

### 4.2 请求、错误与限流

- 继续使用 Bearer、成功 `{ok:true,data}`、失败 `{error:{code,message}}` 与 `Cache-Control: private, no-store`。先凭证、矩阵与权限检查，再有界读取请求体。仅接收 `application/json`，正文上限 16 KiB；即使没有 `Content-Length` 也要限制读取，严格对象、不收未知字段、不收批量；ID 为十进制正安全整数。
- 沿用 400/401/403/404/429/500。有效令牌缺端点权限或主体全局权限为 403；无目标与越权目标统一 404。错误码在 `lib/manage/errors.ts` 集中登记；新增 409（版本/状态或幂等冲突）、413（过大）、415（媒体类型不支持）、503（写入口关闭）。429 保留 `Retry-After`。
- 写请求单设令牌及用户桶，起始拟定 10 次/分钟/令牌、30 次/分钟/用户；保留可信 IP 前置防护。进程内频控仅承诺单实例语义。写入口设独立开关，默认关闭，紧急停写不影响九个读端点，也不回滚已提交的数据。

### 4.3 幂等与审计

- 两条写端点必传 `Idempotency-Key`（16–128 个受支持的 ASCII 字符）。按令牌＋端点＋键隔离，绑定规范化目标和参数指纹；授权和目标可见性通过后才能回放。24 小时内同键同请求返回已提交的成功响应，不再改业务、审计或发事件；同键不同请求返回 409。超期无回放承诺，客户端应先读确认，不盲目重试。
- 用唯一键串行化同键并发。幂等结果、数据变更、业务审计和 outbox 同事务提交；失败回滚，不留下成功记录。使用现有调度基础设施有界清理过期记录。
- **调用记录不等于变更审计**。变更审计随业务事务提交，至少标识 `via=api`、操作者、受控的令牌尾号/请求关联 ID、目标及前后值。不记录 Bearer、完整哈希、幂等键、正文或原始请求体。相同目标的锁定空操作与成功回放不产生重复变更记录。
