## 1. 目标

把站点注册从「邀请制 / 开放」的单选，改为**两个独立开关 + 可选的邮箱验证登录门**：

- 站点设置里**开放注册**与**邀请注册**各自独立开关，四种组合都有明确行为（§4）。
- 两个开关都关时有明确的「不开放注册」状态与提示。
- 开放注册可设置邮件验证；**要求验证的账号不验证就无法登录**，并且被拦的用户有免登录的自救路径。

与排期无关：即使没有任何排期方案，这些也要成立。

## 3. 四种开关组合的行为（站长 Q7、Q8 已确认）

| 开放 | 邀请 | 注册页 | 注册 Action |
|---|---|---|---|
| 关 | 开 | 邀请码必填（等同现状的邀请制） | 必须带有效邀请码，沿用邀请码尝试限流 |
| 开 | 关 | 无邀请码栏（等同现状的开放注册） | 开放注册规则；IP 限流 + 未知 IP 全局兜底桶 |
| 开 | 开 | 邀请码栏保留，**选填** | 填了有效邀请码 → 邀请注册规则；留空 → 开放注册规则；**填了无效邀请码一律报错，不降级成开放注册** |
| 关 | 关 | 显示「当前不开放注册」，不显示表单 | 一律拒绝，**不消耗任何限流名额**；登录、找回密码、验证链接不受影响 |

「双开且填了无效邀请码」报错而不降级，是为了防止访客试探邀请码时被悄悄放行成开放注册，也让邀请码尝试限流仍然有意义。

## 4. 范围与 Step 分解

**Step 0 · schema：登录门标记列（迁移 0024，站长 Q11 已确认）**
- `users` 新增一列（暂名 `login_verification_required`，`boolean NOT NULL DEFAULT false`），**只在注册时**按策略写入，改绑邮箱不动它。
- 历史账号默认 false，因此导入的 10,698 个用户天然不受登录门影响。表数不变（54），列数 +1；`db:verify` 与相关计数断言同步。
- 应用到开发库 `qysub_next` 前须经站长确认，并核对用户数不变（见 §8）。

**Step 1 · 策略键与读取（兼容旧数据）**
- 新增 `register.policy`：`{ open: boolean, invite: boolean, verifyEmail: boolean }`，zod `.strict()` 校验，坏配置整体回落默认（同 `limits` 口径）。
  `verifyEmail` 只有一个含义：**开放注册的账号必须验证邮箱才能登录**（站长 Q12，不再分层）。
- 旧 `register.mode` 读兼容：`invite → {open:false, invite:true, verifyEmail:false}`，`open → {open:true, invite:false, verifyEmail:true}`
  （旧开放模式本来就强制验证，保持行为一致）；写入新键后旧键不再参与判定，**不做破坏性迁移**。
- 旧 `email.verification`（`open_only` / `always`）被本策略取代，**不再读取**。该键在开发库从未设置过，`always` 无人使用；
  需在 CHANGELOG 明确记录「`always`（邀请注册也验证）选项移除」这一行为变化。
- 默认值必须等价于现状（邀请制），升级后站点行为零变化。

**Step 2 · 站点设置界面**
- 把 `/admin/settings` 的注册单选与「邮箱验证策略」两块合并为一块：「开放注册」「邀请注册」两个独立开关 + 「开放注册需验证邮箱」一个选项。
  保存同事务审计；错误码与文案成对（G-15）。
- 两个开关都关时，界面给出明确的「将不开放注册」警示，避免误操作。

**Step 3 · 注册页与注册 Action 按四种组合分支**
- 按 §3 的表实现，含「双开选填」「关闭态不消耗限流」。
- 每个分支至少一条错误路径用例（G-16）。
- **要求验证的账号注册后不再自动登录**：注册成功只写用户行与标记、发验证邮件，**不调用 `establishLoginSession`**，
  跳到「请查收验证邮件」提示页（现状是注册完直接登录再提示，与登录门矛盾，见 §2）。不要求验证的账号（如邀请注册）保持现状，注册即登录。
- 写入：要求验证时同时写 `login_verification_required = true`（新列）与 `emailVerificationRequired = true`（沿用旧列，
  继续负责写权限门，改绑邮箱仍只动旧列）。

**Step 4 · 登录验证门（站长 Q9 已确认）**
- `LoginOutcome` 新增失败分支（如 `unverified`），登录页给出明确提示，不再笼统显示「用户名或密码错误」。
- **判定口径（实现时更正，2026-11-04）**：**只看 `login_verification_required` 一列**，为真就拦。原先写的「且 `emailVerifiedAt` 为空」被去掉了——
  门放在 `createSessionInTx`，标记在**首次验证成功时由 `consumeEmailTokenInTx` 在同一条 UPDATE 里清除**，所以「标记为真」已经等价于「尚未完成首次验证」，
  不需要再看 `emailVerifiedAt`。这同时修掉了原设计的一个漏洞：若标记不清除，早已验证过的用户改绑邮箱（会重置 `emailVerifiedAt`）后会被重新拦住。
  不是「未验证即拦」（否则 10,698 个导入用户被一次性锁死），也不看 `emailVerificationRequired`（改绑邮箱会置真它，Q9(b) 要求改绑不拦登录）。
- 门放在 `createSessionInTx`（唯一会话创建入口），覆盖密码登录、reset/claim、注销撤销三条路径。注销撤销遇到门时**撤销照常成功、只是不建会话**
  （与封禁一致），否则抛错会让整个撤销事务回滚。
- **只拦新登录，不踢现有会话**：已登录的未验证账号现有会话不受影响，登录门上线后新注册的账号才受约束，历史账号零影响。
- 密码校验必须**先于**验证状态判定：密码错的人只看到「用户名或密码错误」，不能借「未验证」提示探测账号存在与状态（防枚举）。

**Step 5 · 免登录重发验证邮件（站长 Q9 已确认；没有它 Step 4 不得上线）**
- 登录被拦的页面提供「重发验证邮件」入口，沿用忘记密码的**中性响应**（不暴露账号是否存在）与既有邮件令牌限流。
- 令牌沿用现有 `verify` 用途与 24 小时有效期；重发使旧令牌失效的语义保持现状。

**Step 6 · 收口**
- 门禁：四种开关组合 × 邀请码有无的集成与 E2E；登录门只拦「要求验证且未验证」，导入用户登录不受影响；
  被拦用户能通过免登录重发完成验证并登录；THEME 无关，回写 CHANGELOG 与 ROADMAP。

## 5. 边界（明确不做什么）

- 不做排期（M11.4）：本里程碑不改 `campaigns`、不加 effect。
- 不做邮件定向发放邀请码、会员自助发码；邀请码生成仍只在 `/admin/invites`。
- 不踢已登录的未验证账号的现有会话；不回溯修改历史账号的验证要求。
- 不改写权限评估器：写权限的邮箱验证门（`evaluator.ts:110-118`）保持现状，登录门是它之外的新增一层。
- 改绑邮箱造成的重新验证**仍只拦写权限、不拦登录**（Q9(b)），避免用户填错邮箱后被永久锁死。

**已知限制（不在本里程碑解决）**

- **注册时邮箱填错的用户无法自救，站长也没有后台手段处理。** 验证邮件发到错误地址，登录被门拦住，免登录重发也发给同一个错误地址；用户名同时被占用。
  已核实 `/admin/users` 的现有能力只有：创建/解除限制、授予/撤销角色、吊销会话、处理申诉——**没有删除账号，也没有手动标记邮箱已验证**。
  所以目前唯一的出路是直接改库。这是登录门带来的真实运营缺口，建议后续单独立项，候选方案：后台「手动标记邮箱已验证」、
  或「超过 N 天未验证的账号自动清理以释放用户名」。本里程碑不做，避免范围继续扩大。
- 开放注册要求验证后，**注册即登录的行为消失**：要求验证的新账号注册后跳登录页等邮件验证。这是用户可见的变化，已记入 CHANGELOG。
- `email.verification` 的 `always`（邀请注册也验证）已移除；开发库该键从未设置过，无现存站点依赖。
