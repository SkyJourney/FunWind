# M9.5 · 后台管理体验专项（侧栏布局 + 列表分页筛选 + 交互基线统一）

- 阶段：M10.9 之后的插入里程碑（编号顺 M9「管理后台」主体，沿用 M10.5/M10.6 插入惯例）｜ 状态：⬜ 设计稿完成，**待站长确认待决项（§7）后开工**
- 来源：站长 2026-10-29 指示——「后台管理专项：探查管理形态与交互形态，整理修订优化清单，先写好里程碑文档」。站长点名：用户管理默认不查询列表、大多数列表没有分页、大部分列表没有筛选项、PC 端左侧导航没有侧栏感、移动端列表有溢出可视区的地方；定位为「**PC 是后台大本营，每个菜单的管理交互要做好；平板/手机端重点优化视觉与交互**」。
- 依据：本文档 §2 现状审查（2026-10-29 对 `/admin` 全部 16 个页面 + 布局壳 + 服务层的逐页代码精查，证据均带文件行号）；界面基线沿用 M10.5（Tailwind 语义色 / EmptyState 约定 / ConfirmSubmit）。

## 1. 定位与边界

- **只做体验**：不动权限模型（28 权限点）、不动数据库 schema、不改任何 Server Action 的鉴权与审计语义；新增的查询能力（分页/筛选/搜索）只加服务层查询函数。
- **前台零影响**：全部改动限定在 `/admin/*`、`components/admin/*`、`lib/admin-*` / 各域 admin 服务层；唯一共用组件 `content/pagination.tsx` 只读复用。
- **PC 优先**：每个菜单先把桌面端管理交互做对；平板（768）/手机（375）以「不溢出、可操作、信息可达」为底线做专项巡检（§3.6）。

### 2.4 逐页精查清单（16 页）

> 「缺陷」指明确的行为问题；「改进」指体验提升。分页/筛选/确认/空态等共性项不重复罗列，只标共性问题编号。

**用户与权限域**

- **users（用户管理）**：缺陷——默认空页（§2.2）；`limit(20)` 无分页。改进——列表增加注册时间/主题帖数展示（已有数据）；支持按 uid 精确跳详情；结果含邮箱/状态供辨识（管理员场景）。
- **users/[uid]（用户详情）**：缺陷——台账取回 20 条只渲染 5 条，卡片标题却写「最近 20 条」（users/[uid]/page.tsx:256,261）；台账固定第 1 页无翻页（:41）；限制过期判断用字符串比较（:140-141）；授角色裸填板块 ID（:217-224）。改进——台账完整分页；板块作用域改下拉；会话/角色/限制信息卡化。
- **authz（角色列表）**：缺陷——删除自定义角色无确认（C3，级联删除却最危险）；删除前看不到影响面（授权数/持有人数服务端算了只进审计，authz/admin.ts:226-229）。
- **authz/[roleKey]（授权矩阵）**：缺陷——授权在主矩阵、撤销在页底另一张表，入口分裂（:115-122 vs :131-154）；已授权再点只是幂等重复授权；每权限点一次提交整页刷新；撤销无确认（C3）。改进——每行 toggle 双向（已授权即显示撤销）；按 resource 分组折叠；作用域 select 自动提交。
- **authz/forum/[fid]（板块视角）**：缺陷——table 无 overflow-x-auto（§2.2 溢出实锤）；纯只读却无「去修改」出口，两个视角页互无链接；无板块切换器，只能拼 URL。

**内容治理域**

- **review（内容审核）**：缺陷——队列 `limit 50` 静默截断无分页；无按板块/类型（主题/回帖）/时间筛选；无批量通过/驳回。改进——高频页按「大本营标准」重做：卡片信息增强（内容摘要行）、板块筛选、批量操作。
- **reports（举报处理）**：缺陷——`reportQueue(tab)` 无分页无上限防护；无板块/时间筛选；无批量忽略。改进——状态 tab 保留，补分页与筛选。
- **poll（投票管理）**：缺陷——N+1（C9）；`limit 50` 不可见旧投票；关闭后无重开入口（误关只能动库，admin.ts:16 注释自认）；删除是不可逆三表删除但确认弹窗无影响面提示。改进——重开投票需要新 action（低风险，纳入）。
- **pm（私信管理）**：缺陷——uid 筛选是内存过滤，语义系统性遗漏（C2 最严重实例）；筛选只认数字 uid；统计双全表 COUNT（C9）。改进——筛选下推 SQL（支持用户名反查）；统计加缓存。
- **announcements（公告）**：缺陷——**公告无编辑能力**，改错别字只能下线重发（announcements/page.tsx:52-106 只有创建+下线）；`limit 20` 写死历史不可达；导航/友链/页脚是裸 textarea 逗号分隔，无校验无排序；时间原样输出 DB 字符串，与 invites 的 fmtDate 口径不一（:129）。

**运营域**

- **invites（邀请码）**：缺陷——无状态 tab（可用/已用/过期混排）、无批次筛选、`limit 100` 后旧码不可管理；生成成功后新码不高亮不置顶无一键复制。改进——补「复制」按钮（clipboard API 小客户端组件）与 `?batch=` 高亮。
- **badges（徽章）**：缺陷——字典空时页面静默空白（C5）；授予无确认且不可撤销（无收回徽章能力，服务层也没有）；无授予记录列表。改进——补收回徽章 action（记审计，复用现有 user_badges 表）；用户定位接 UserPicker。
- **points（积分管理）**：缺陷——手工调整（可负）无确认（C3）；调整后无最近调整记录展示，无法在本页核对台账；用户名手输（C7）。
- **logs（审计日志）**：后台标杆页（唯一分页+筛选+CSV）。改进——分页换页码组件；详情 JSON 列加展开查看（现在是 `max-w-md truncate` 一行）；时间列宽在移动端优先保住。

**系统与站点域**

- **settings（站点配置）**：缺陷——单页 7 表单 400 行无锚点无分签；SMTP env 未配置时显示默认 `smtp://127.0.0.1:1025` 管理员无法区分「没配」和「配了本机」（page.tsx:41,89）；频控只展示 member/admin 两角色，其他角色配置「保存时原样保留」但不可见不可改（:389）；秒数单位无换算辅助（editWindowSec 默认一年=31536000）。
- **logo（LOGO 管理）**：缺陷——上传链路断裂：超 512KB 让管理员线下跑 `scripts/logo-resize.py`（page.tsx:15,44），页内无预校验无压缩；上传成功新项无高亮。改进——客户端文件大小预校验 + 提示文案修顺。
- **forums（板块管理）**：缺陷——双全表查询可合一（C9）；错误横幅 `?err=` 刷新复活；父级下拉全角空格缩进层级不可读；深层板块内联 paddingLeft 窄屏挤压。
- **forums/[fid]（编辑板块）**：缺陷——无「未保存更改」保护，误点返回丢全部编辑；前缀空态违反 EmptyState 约定（C5）。
- **emojis（表情管理）**：缺陷——组内表情查询无上限，500 枚 ≈ 2500 个 form 节点 DOM 失控；排序逐位 ↑↓ 整页刷新（C6 最痛实例）；批量上传失败只有单条错误无逐文件明细；空态手写灰字（C5）。改进——组内表情分页（20/页）+ 数字输入排序范式 + 上传逐文件结果明细。
- **dashboard（看板）**：缺陷——3 全表 COUNT 实时执行（C9）；柱状图单日值仅 hover title 移动端不可触达、无 Y 轴刻度；时间窗口硬编码 30 天。改进——统计加 60s 内存缓存；柱状图加最高值/均值标注行；卡片加环比箭头（数据已在手，纯展示计算）。

## 3. 设计

### 3.1 后台布局壳（Step 1）

`AdminShell` 重做为经典后台骨架，脱离前台 `max-w-6xl` 容器：

- **PC（≥lg）**：左侧固定侧栏（`lg:fixed lg:inset-y-0 lg:left-0 lg:w-56`，`bg-card` 底 + `border-r`，独立滚动），站点名「清风社区 · 后台管理」置顶；内容区 `lg:pl-56`，内部再给 `max-w-5xl` 控制行宽。侧栏不再依赖前台 header 的 `sticky top-20`。
- **平板（md）**：侧栏收窄为图标栏（`w-14`，icon + title tooltip），悬停展开——平板横屏保住内容宽度。（若站长嫌复杂可退化为：md 仍走抽屉。待决项 §7-1）
- **手机（<md）**：保留汉堡 + Sheet 抽屉，抽屉内导航分组视觉与 PC 侧栏一致；顶栏加当前页标题。
- 导航激活态增强：左侧 2px 主色竖线 + `bg-accent`；二级页（users/[uid]、forums/[fid]、authz/*）给「父项也高亮 + 页内返回面包屑」。
- 二级页统一加页头：`← 返回xxx` 链接 + 标题 + 关键统计（如 users/[uid] 显示注册时长/主题帖数）。

### 3.2 列表基建（Step 2）

- **分页**：服务层统一约定 `listXxxPage(filters, page) → { items, total }`（`PER_PAGE=20` 后台默认常量，logs 维持 50）；页脚统一 `共 N 条 · ` + 复用 `content/pagination.tsx`（basePath 携带现有 query）。全量列表页（板块树、角色列表、徽章字典、LOGO 池、分组列表）属天然小集合，**不做分页**，只做查询合并与防护说明。
- **筛选栏**：统一形态 `AdminFilterBar`（服务端组件）：GET 表单 + 关键词输入 + select 筛项 + 「筛选/重置」；筛选状态持久在 URL。每个列表页筛项按业务价值定（§4 各步明细），不追求大而全。
- **排序选择**：高价值列表给 `?sort=`（如 users：注册时间/uid/主题数；invites：创建时间/过期时间）。默认排序维持现状。
- **空态**：巡检全部违反 EmptyState 约定的手写灰字，统一换 `EmptyState`。
- **Flash 反馈**：统一 `AdminFlash` 组件（读取约定 searchParams 渲染，`role="alert"`/`role="status"`，成功条带关闭按钮；URL 回显模式保留——这是 Server Action redirect 的自然产物，不引入新机制）。新增写入类操作成功后通过 `#anchor` 或高亮参数定位新项（invites 批次、logo 新项）。

### 3.3 交互基线

- **确认保护矩阵**（定成规则写进 CLAUDE.md 收口时）：删除/级联删除/撤销授权/收回角色/积分调整（含正负）/施加或解除用户限制/收回徽章 → 必须 `ConfirmSubmit`；开关/排序/低风险保存 → 直接提交。本次补齐 4 处缺失：角色删除、授权撤销、积分手工调整、徽章授予（徽章另加「收回」操作同样走确认）。
- **UserPicker**（Step 2 基建）：原生 `<datalist>` 方案（零 JS）：输入用户名 → datalist 提供用户名+uid 选项，提交仍传用户名由服务端解析。替换 badges/points/pm/users 四处手输。不做 JS 搜索下拉（遵循服务端优先，控制复杂度）。
- **板块选择器**：`ForumSelect`（服务端组件，按权限过滤的 `<select>`，层级缩进用 `&nbsp;` 修复全角空格），替换 users/[uid] 的裸板块 ID 输入与 forums 父级下拉。
- **排序范式统一**：emojis 的逐位 ↑↓ 改为「sortOrder 数字输入 + 单条保存」（与 forums 范式一致）；分组数少维持 ↑↓ 可接受——统一为数字输入，删 ↑↓。不做拖拽（范围外）。
- **批量操作**：只做两处明确收益的——审核队列「批量通过/驳回」（checkbox + 一次 Server Action 事务）与邀请码「按批次撤销」。其余列入范围外。

### 3.4 逐页改造（Step 3–6 落地，明细对应 §2.4 清单）

每页按「缺陷全修 + 改进按 §4 批次标注执行」，实现时以 §2.4 行号为线索逐条销账，收口时在本文档勾选。

### 3.5 性能修正（Step 7）

| 问题 | 方案 |
|---|---|
| 投票列表 N+1（≈101 SQL） | 选项数/票数改两条聚合子查询（或 GROUP BY join），一次出列表 |
| pm uid 筛选内存过滤 | 下推 SQL：`WHERE sender_id = ?` + 用户名反查 uid 后筛选；分页随之自然解决 |
| pm 统计双全表 COUNT / dashboard 3 全表 COUNT | 60s 进程内缓存（复用 authz snapshot 的 TTL 模式） |
| forums 双全表查询 | threadCount 并入主查询（LEFT JOIN + COUNT 子查询） |
| emojis 组内无上限 | 组内表情改分页（20/页）+ 关键词过滤 |
