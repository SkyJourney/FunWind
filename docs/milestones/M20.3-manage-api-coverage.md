- 阶段：四·运营与演进 ｜ 依赖：M20.2（权限矩阵、写管线、幂等与验收基建，已全部合入 `main`）。
- 状态：Step 0–4 已合入 `main`；Step 5–6 本地隔离验收与独立复审通过（2026-11-20），待提交及 CI。生产未部署，生产写入口未开启。
- 实际范围：管理 REST 从 11 个端点（9 读、2 写）扩展为 **21 个域、82 个端点（30 读、52 写）**。准确的方法、路径、参数和权限见[管理 REST 契约](../MANAGE-API.md)；[M21](M21-admin-mcp.md) 只消费已发布且已验收的契约。

## 1. 基线与探查结论

后台共 19 个管理域、约 60 项操作（菜单 6 组 25 项 + 非菜单管理路由）。约 3/4 的服务层已显式 actor 分离（事务+审计完整），可直接按 M20.2 模式接入；公告三操作、表情九操作、板块图上传、测试发信仍内联在 Action，需先抽服务。带 revision 乐观锁的域：主题包、运营排期、运维任务；其余靠行锁/状态机/唯一键。

M20.2 的写管线已通用：`manageEndpoint` 门禁（方法比对、写开关、写频控、调用审计）对新端点零改动可用；`runIdempotentManageWrite` 与端点无关；`parseManageWrite` 的路径参数已参数化；签发矩阵、在线文档骨架、`whoami` 诊断随权限目录自动扩展。

## 2. 明确不做

- 令牌自管理 REST（凭证管理不经凭证自身，M20 已定）。
- **文件上传类操作**：表情上传、板块图、品牌素材（LOGO/Hero/Decor 池）、主题包导入与素材替换——multipart 超出当前 JSON 写协议，留待单独评估；其对应的 JSON 元数据操作（改名/排序/启停）在范围内。
- 跨服务运维恢复、备份同步执行（归 ops 管线自有 API）；REST 只做任务受理与配置。
- 批量事务端点：客户端按幂等键逐条循环，不提供单请求多目标事务。
- 积分发放规则之外的系统级写；测试发信（副作用是真实外发邮件）。

## 4. 技术方案

### 4.1 服务接入模式

沿用「prepare（事务外鉴权/范围）→ 幂等事务内 lock（锁内复验归属与状态）→ execute（真实变更）」。每个新写域产出 `prepareApiXxx`，REST 与后台 Action 双入口共用同一事务核心，后台行为不变。带 revision 的域以 `expectedRevision` 映射 409；无版本域以行锁+状态复验兜底，**不新增 schema、无迁移**。

基建泛化（Step 0）：`commitWrite` 的 endpoint 参数泛化为 `ManageEndpointId`；`requireSuccess` 错误码映射改为各 Service 模块注册码表（新拒绝码不再落 internal）；`ManageEndpointDefinition.permission` 联合扩展。

### 4.2 事件重放安全

每个新写域接入前核对其 outbox 消费者重放幂等（站内 dedup 键唯一性：`restriction.changed`/`role.changed`/`badge.*` 等既有键）。不足者按 `moderation_notification_v1` 模式登记投递策略（预期极少）。

### 4.3 文档、守卫与验收的扩展

- 自动跟随：在线文档骨架/导航、`whoami` 诊断、签发矩阵（含「尚无写端点」提示）。
- 手工同步：`ENDPOINT_DOCS`（编译穷举）、`docs/MANAGE-API.md` 端点表（`manage-contract.test` 比对）、总述文案改写（「仅内容域可写」等表述作废）。
- E2E 实际覆盖：矩阵 30 档 × 82 端点（2,460 次 HTTP 探测，60 枚令牌分摊到 15 位专用管理员）；全部 52 个写端点逐项经过停写门禁；查询验证具体夹具与有意义的参数拒绝，写入按域验证代表性状态迁移和副作用。矩阵与停写均由 CI 常态执行。
