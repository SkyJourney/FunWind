# M7 · 游戏化（积分/等级/勋章/签到）

- 阶段：二·核心 ｜ 覆盖模块：M07 ｜ 依赖：M6（需要真实事件流）
- 状态：⬜ 未开始

## 目标

游戏化四件套作为**模块注册表的第一个真实消费者**落地：credits（账户/流水）、等级引擎（旧 points 阈值 + 魔界称号）、
medals、checkin（每日红包）。既兑现情怀数据，又验证内核的插件化承诺。

## 范围（做什么）

1. **credits 模块**：账户（users.credits JSON 已迁）+ 流水表（credit_logs 93,765 条已迁）+
   `credit.grant/deduct` API + 消费 `thread.created/replied` 等事件自动发放（规则配置化）。
2. **levels 模块**：等级 = f(主积分)，阈值沿用旧 `groups.points`（LV1.魔狱原住民 150 → LV12.圣魔王 18,000），
   称号展示于资料页/帖子页；升降级触发事件。
3. **medals 模块**：25 枚勋章/持有关系已迁；授予 API（手动 + 条件自动各留接口）+ 勋章墙页面 + 帖子页佩戴展示。
4. **checkin 模块**：每日签到（北京时间自然日边界）+ 连签计数 + 奖励（旧「每日红包」+5 青翼币语义）+
   签到日历组件（帖子页侧栏槽位——消费 M2 槽位机制）。
5. 全部四个功能以 `defineModule` 实现：各自注册事件消费、槽位、权限点（如 `checkin.do`）、路由。

## 边界（明确不做什么）

- 不做银行/抽奖（M14 遗珠，P3 另立项）；不做积分商城/兑换。
- 不做任务系统全量（旧 5 任务中「新人报到/头像/资料」类条件任务留到 M9 后按需做）——本期只做签到。
- 不做跨模块积分对账后台工具（M9 审计日志覆盖）。

## 测试规则

- 单测：发放幂等（同一事件重复派发不重复加分）、并发发放（竞态用事务/唯一键约束验证）、
  等级边界（阈值±1）、签到时区边界（23:59:59 / 00:00:01 北京时间）、连签中断重置。覆盖率 ≥90%。
- 集成：与旧数据对账——随机抽 50 用户，`credits` 合计 + 迁移流水重放结果一致。
- E2E：签到→积分入账→等级变更→勋章授予（手动）→展示位更新；模块装卸回归（禁用 checkin 模块后槽位消失、积分主体不受损）。
