## 2. Step 0 实测结论（2026-10-28，dev :3100，Playwright / Chromium）

- no-preference：首页前 10 张卡片挂 `.fw-enter`，延迟 0/50/100ms…，`document.getAnimations()`=10，动画正常。站长看到的「依次上划」即此项。
- reduce：`animationName: none`、动画数 0——与设计一致。
- `document.startViewTransition` 存在（Chromium 支持）；站长两端均未开 reduce，**手机浏览器型号待确认**（Safari < 18 无 VT API，会静默降级为无过渡）。
- `withViewTransition` / `captureTransitionOrigin` 在业务代码零引用，只在 `app/design/motion/motion-demo.tsx`。
- 路由层：`nav-kind-capture → template.tsx` 只做**进场**（push 自右 / pop 自左），无退场。
- 站长此前「全都没有」的合理解释：验收期恰逢 `allowedDevOrigins` 拦截全部客户端 JS（方向接线依赖客户端）；该根因已在 M10.6 修复轮解除。其余项是真实缺口。

### 5.6 慢网络与失败兜底验证（2026-10-28，站长追加要求）

站长要求：慢网络下点击要**立刻有响应**（否则会重复点击），等待要有占位；加载失败要 toast「加载失败，请重试」，且**页面回到动画前的页面**。

| # | 验证项 | 结果 |
|---|---|---|
| F1 | 网络失败时 Next 的原生行为（拦截目标页 RSC 请求） | ⚠️ 控制台 `Failed to fetch RSC payload … Falling back to browser navigation`：**退化为整页硬跳转**，真实断网会掉进浏览器错误页，不会留在原页面 |
| F2 | 用 Navigation API `navigate` 事件对**跨文档**导航 `preventDefault()`（Next 软导航是同文档 pushState，不受影响） | ✅ URL 与页面内容都停在原页，且能拿到被拦下的目标地址（= 失败信号）；之后点别的链接软导航正常、重试失败的链接也成功，**路由器没有卡死**；残留的 `data-nav` 必须在失败时清掉 |
| F3 | 给「导航型 RSC 请求（非预取）」包 `AbortSignal.timeout`，把「卡住」转成失败 | ✅ 服务端卡 6s、超时设 1.5s：1.6s 内中止 → Next 回退整页跳转 → 被 F2 的监听拦下，页面留在原页 |
| F4 | 浏览器返回（popstate）到访问过的页面 | ✅ **0 个 RSC 请求**：Next 直接从路由缓存还原，即时且不会失败；仅「目标页被缓存淘汰」才可能失败，做成尽力而为 |

**兜底三层（方案）**：
1. **立即反馈**（所有浏览器）：点击即在顶部出一条进度条（80ms 内可见）、被点元素置 busy 态（卡片压暗 + 转圈）、同一目标在途时忽略重复点击；超过 3s 追加「网络较慢，仍在加载…」提示。
2. **失败检测**：`navigator.onLine === false` 时点击前直接 toast 并不发起导航；在途的导航 RSC 请求 15s 超时（F3）；Next 回退整页跳转被 `navigate` 事件拦下（F2）→ 统一进入失败处理。
3. **失败处理**：toast「加载失败，请重试」（带「重试」按钮重新发起同一导航）、清除进度条与 busy、清掉 `data-nav`；页面留在动画前的页面（因为过渡只在提交时才开始，失败的导航根本没有动画，无需回滚）。

**局限**：Navigation API 在 Chromium 全面可用，Safari / Firefox 较新版本才有；不支持的浏览器上第 1 层与 `onLine` 预检仍生效，但「服务端 5xx / 超时」的整页回退拦不住，退化为 Next 默认行为（浏览器错误页）。占位用进度条 + busy 态，**不用路由级骨架屏**：仓库红线要求 404 能力路由（`/t`、`/f`、`/u` 等）不得有 `loading.tsx`（否则 404 变 200）。

**与旧方案对比**：现行 `template.tsx` 只能**进场**（Next 无退场钩子），所以「划出 / 返回收起」从未存在；`<ViewTransition>` 由浏览器同时持有新旧两张快照，退场与扩散 / 收起都能做。

**尚未验证（集成时必须逐项验证，冻结帧截图为证）**：
- 顶栏 / 底部 Tab 的叠放：命名组默认画在 root 之上，滚动过的长页会盖住吸顶顶栏——官方做法是给它们各自 `view-transition-name` + 更高 `z-index`；
- 带 `loading.tsx` 的页面（/boards、/search）：目的页先 Suspense 再出内容时，过渡作用于骨架；
- Safari / iOS：过渡类型与 `view-transition-class` 需 Safari 18.2+，更低版本静默降级为无动画（站长手机型号仍待确认）；
- Router Cache 命中与否对「返回」观感的影响。

### 5.7 Step 4b 实测发现：popstate 不触发页面过渡

- **方案成立（点击路径）**：`template.tsx` 一处挂 `<ViewTransition>` 即可覆盖全站——template 每次导航重挂载，进退场照样触发，且位于 layout 之内，顶栏 / Tab 天然不在页面动画组里。真实路由实测：首页→主题 push（旧页 150ms 左出 / 新页 400ms 右入）、首页→板块目录 push、板块目录→搜索 fade（淡出 150ms / 淡入 250ms）、搜索→首页 pop；仅查询串变化（筛选）不触发。滚动过的长页做过渡时，冻结帧证实顶栏始终在最上层、没有被页面内容盖住。
- **发现（浏览器返回）**：`history.back()` / 返回键 / 返回手势在路由缓存命中时 **不启动 View Transition**（给 `document.startViewTransition` 打桩计数为 0，也没有 RSC 请求）。与 `template`、与是否有导航守卫都无关——根因在 React 源码 `shouldAttemptEagerTransition`：popstate 里启动的过渡会被**同步急切提交**（为保住滚动恢复），同步提交不走 View Transition。官方文档的「popstate 不带过渡类型」只说对了一半：缓存命中时连动画都不会有。
- **早先验证 5 为何当时触发**：那次返回目标需要重新请求（异步提交），React 无法急切完成，走了普通过渡；缓存命中的返回则不会。所以 §5.5 验证 5 / 验证 7 的结论需要加上这个限定：**popstate 方向属性只在「返回需要异步取数」时才有动画**。
- **影响**：浏览器返回键 / 手势返回基本无动画（瞬时切换）；站内的「返回」类链接（面包屑、顶栏首页、详情页返回箭头等）是普通导航，有 pop / 收起动画。iOS Safari 的边缘滑动返回本身带系统原生动画，再叠加我们的动画反而重复。
- **可选方案**（待站长拍板）：**A 接受**——站内返回控件动画，浏览器返回键保持原生瞬时切换（最稳）；**B 模拟**——popstate 时捕获阶段拦下、在 `document.startViewTransition` 的更新回调里重放 popstate，把 Next 的同步提交挪进 VT 更新阶段（桌面 / Android Chrome 可行，但是 hack，且 iOS 边缘手势会与系统动画重复，需真机验证）。

**4a 实现注记**：
- 失败检测靠三件事联动：包装 `window.fetch` 观察「导航型 RSC 请求」（有 `rsc` 头、非预取、非 Server Action）的失败（拒绝 / 超时 / 响应不是 `text/x-component`），记录失败 URL；Next 随后回退整页跳转时，`navigate` 事件里**只拦「刚观察到失败的那个 URL」**，用户主动的整页跳转、同文档导航、过期记录一律不拦，避免误伤；
- 老浏览器兜底：`AbortSignal.timeout` / `any` 不存在时原样透传（兜底功能绝不能让正常导航抛错）；
- 非页面链接（`/files/`、`/api/`、`/emoji/`、`/brand/`）、下载链接、外链、新标签页、带修饰键的点击都不处理；
- 浏览器前进 / 后退（popstate）失败是尽力而为：F4 证实已访问过的页面不发请求；缓存淘汰时失败则「重试」= 整页加载，让地址栏与页面一致。

**验证页处置**：`apps/web/src/app/design/vt-spike/`（开发专用、有 404 守卫）暂未入库；方案确认后并入 `/design/motion` 升级为动效实验室，或删除。

- **顺带修复**：`/follows` 的数字分页原先 `basePath="/follows"` 会在翻页时丢掉 `?type=` 筛选；现无 JS 兜底翻页已保留类型（E2E 断言）。

  - `StreamList` 泛化：支持游标模式（`cursorParam`/`startCursor`，响应带 `nextCursor`）、复合去重键（`getKey`）、容器元素（`as="ul"`）。通知与公告各有自己的 id 序列，所以通知流用 `kind:id` 复合键。
  - 通知「已读」就地生效（站长拍板）：行改为客户端组件，表单保留（无 JS 仍是 Server Action + 重定向），有 JS 时拦截提交走 `/api/notifications/read`，成功后 `router.refresh()` 刷新页头与分类计数；行数据由服务端 `toNotificationRow` 预渲染（首屏与追加页同一函数，文案模板与原始 data 不下发）。公告的「已读」语义是读全部公告：已追加的其它公告行在下次进入页面前保持原样。
  - 私信会话列表：新增 `conversationPage`（每页 20，取 +1 判 hasMore，排序加会话 id 作第二键），消除旧入口 `conversationList` 对 50 个会话的静默截断；旧入口口径不变。未读数与预览是请求时刻的快照，追加页不实时刷新。
  - 通知游标沿用 `listFeed` 既有的 `createdAt` 严格小于语义：同一秒产生的多条通知若恰好跨在两页边界上会被漏掉——这是**预先存在**的行为，流式加载没有加重也没有修复；若要根治需把游标改成 `(createdAt, id)` 复合游标，列入遗留。
- **Step 3c 取舍**：
  - **顺带修复一个旧缺陷**：聊天页注释写「取尾页（最新在底部）」，实现却是 `page` 缺省 1 = **最旧的 30 条**，会话超过 30 条时打开看到的是最早的消息、发完一条也看不到自己刚发的。现改为默认展示最新一批并停在底部。
  - 消息用 **id 游标**（`id < before`，多取 1 条判 hasMore）而不是页码偏移：消息只增不改，新消息到达不会让「更早」的边界错位。旧的 `conversationMessages(page)` 保留（`m10-admin.int.test` 在用）。
  - 无 JS：顶部是「查看更早的消息」真链接（`?before=<最旧 id>`），历史窗口页带「回到最新消息 →」。旧的 `?page=` 参数不再被聊天页识别（该 URL 形态不在冻结清单内）。
  - 进入时滚到底部发生在水合阶段（布局副作用）：服务端 HTML 先以顶部位置显示、水合后跳到底部，有一次很短的位置跳变；用 `useLayoutEffect` 保证它先于观察器订阅，避免顶部哨兵在 scrollY=0 时误触发加载。
  - 补偿滚动与浏览器原生滚动锚定会叠加（Safari 没有原生锚定），所以聊天页期间在 `<html>` 上设 `overflow-anchor: none`，离开时还原。
- 单测分支覆盖率 85.24%，仅高出门槛 85% 一线：后续新增客户端分支需同步补测。
- 手机浏览器型号待站长确认（决定 VT 在移动端是否生效）。
- 退场与扩散依赖 View Transitions 与现有 `template.tsx` 方向接线共存，同一次导航只能选一种 kind，Step 4 先做技术验证。
